# LSC 功能全清单与必要性评估

> 目的：回答一个问题——**程序中每个功能是否有必要存在？为了什么而实现？有什么作用？重要性如何？**
>
> 本文件是"功能盘点"底稿（穷尽式枚举），不做取舍决策；取舍结论由后续逐域讨论产生。

## 判定标准

| 等级 | 含义 | 判断依据 |
| :--- | :--- | :--- |
| 🟥 **P0** | 产品存在的前提 | 删掉它，产品不成立或会造成数据损坏/安全事故 |
| 🟧 **P1** | 直接影响可用性、稳定性、竞争力 | 删掉它，产品能跑但会频繁出问题或被竞品碾压 |
| 🟨 **P2** | 体验增强 | 删掉它，用户"能忍"，但体验降级 |
| ⬜ **存疑** | 需论证是否保留 | 与当前架构冲突、疑似遗留、或收益不明确 |

盘点口径：以**代码事实**为准（WebSocket 协议命令 58 条 + Python 核心包 + Electron 主进程 + 前端 UI），非文档宣称。

## 0. 功能全景（五层）

```

```

## 1. 接入层：直播源解析与接入

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **9 个平台适配器**<br>抖音/B站/虎牙/斗鱼/快手/小红书/微博/直链/通用页面 | 把用户粘贴的直播间链接转成可播放的流地址 | 用户输入的链接形态完全不可控；不解析则整个产品无从启动。**这是产品的唯一入口** | 🟥 P0 |
| **Protocol + Registry 注册机制** | 适配器统一契约（`can_handle`/`parse`）单例注册、无状态复用 | 新增平台不动核心代码；无状态才能被高并发复用 | 🟧 P1 |
| **URL 路由器**（host 路由 + 线性兜底扫描） | 按域名快速定位适配器 | 直接决定解析首包延迟 | 🟧 P1 |
| **解析缓存**（成功 30s / 失败 10s TTL） | 缓存解析结果 | 房间列表刷新会高频触发解析，无缓存会被平台判定为爬虫而熔断 | 🟧 P1 |
| **真实媒体探测**（`probe.score_candidate`） | 对候选 URL 做有界真实拉流打分 | 平台常返回多个 CDN 候选，**只有实测才知道哪个真能播**；URL 可达 ≠ 能拉流 | 🟧 P1 |
| **租约机制**（`select_stream_lease` + TTL 提前续期） | 给流地址附带有效期，到期前主动换源 | 平台签名 URL 有时效，临期不换会导致录制中途断流 | 🟧 P1 |
| **虎牙签名 FLV 管道**（Python 拉流喂 FFmpeg） | 用 Python 实现虎牙 JS 签名，再把 FLV 数据管道给 FFmpeg | 虎牙签名无法用 FFmpeg 原生 `-headers` 表达，**不这么做虎牙直接不可用** | 🟧 P1 |
| **画质选择**（原画/高清/标清/流畅） | 按 `QUALITY_PRESET_CANDIDATES` 选流 | 用户带宽/机器差异大；多路并发时必须能降码率 | 🟧 P1 |
| **平台凭据鉴权**（B站 / 抖音 / 虎牙 Cookie） | 保存并注入 Cookie 访问需登录的流 | 部分直播/高画质线路要求登录态，无凭据则拉流失败 | 🟧 P1 |
| **SSRF 防护**（拒绝 RFC1918/loopback/link-local + 重定向校验） | 拦截指向内网的 URL | 用户输入即攻击面；不拦则可被诱导探测本机/内网服务 | 🟥 P0 |
| **Header 长度硬限**（3800 字节） | 截断超长 headers 再交给 FFmpeg | 超长 headers 会让 FFmpeg 直接崩溃，且是**难排查的崩溃** | 🟧 P1 |
| **URL 合法性校验**（`validate_room_url(_s)`） | 添加房间前预校验 | 在输入源头拦截错误，避免脏数据入库 | 🟨 P2 |

## 2. 捕获层 A：录制引擎

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **12 路并发录制** | 同时录制最多 12 个直播流 | 产品定位本身（多视角录制）；单路工具市面上已有 | 🟥 P0 |
| **`copy` 直拷模式** | 不解码直接封装落盘 | 无损 + 近零 CPU + 零代损；**画质是切片工具的生命线** | 🟥 P0 |
| **6 种编码器**（libx264/x265/nvenc/qsv/amf/custom） | 覆盖 N卡/Intel/AMD/纯CPU | 用户硬件五花八门；只支持一种会让半数用户不可用 | 🟧 P1 |
| **硬件优先 + 自动回退** | 优先 NVENC，失败退 libx264 | 兼顾性能与兼容 | 🟧 P1 |
| **断流自动重连**（指数退避 + 刷新 URL） | 网络抖动时重连续录 | **直播必然抖**；不重连则长录制必断，是"能不能挂机"的分水岭 | 🟥 P0 |
| **主动刷新流 URL**（`_should_proactively_refresh_stream`） | 录制中提前换源而非等断 | 被动等待断流意味着每次都要丢几秒画面 | 🟧 P1 |
| **磁盘空间保护**（每路 8GB 预检 / <2GB 安全停录） | 空间不足时优雅停录 | 录满系统盘会**拖垮整个操作系统**，不只是丢录制 | 🟥 P0 |
| **三级优雅停止**（stdin `q` → terminate → 杀进程树） | 逐级升级的停止策略 | FFmpeg 被硬杀会产出**坏 MP4**（moov 未写）；优雅停止是数据完整性保障 | 🟥 P0 |
| **健康检查**（进程退出 + 连续 6 次文件不增长判卡死） | 识别"进程活着但没数据"的假死 | 假死是最隐蔽的故障：界面显示录制中，实际什么都没录到 | 🟧 P1 |
| **录制文件三层校验**（存在 → ≥0.1MB → 文件头 `ftyp`/`FLV`/`EBML`） | 校验产物真伪 | 防止"以为录到了"；校验头才能识别 0 字节/截断文件 | 🟥 P0 |
| **中文友好错误**（`_friendly_ffmpeg_message`） | 把 FFmpeg stderr/退出码翻译成中文 | 用户看不懂 `No space left on device`，看不懂就无法自救 | 🟧 P1 |
| **录制修复**（`repair_recording`） | 抢救崩溃/断电产生的残缺文件 | 长时间挂机场景断电概率不低，能救回比丢弃强 | 🟨 P2 |
| **录制历史**（`recording_history.json`） | 记录历史会话 | 追溯与排障 | 🟨 P2 |

## 3. 捕获层 B：实时预览（MSE / fMP4）

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **4 路并发预览** | 同时预览最多 4 路 | **没有预览就无法定位切片点**，标 i/o 就是盲标 | 🟥 P0 |
| **MSE + fMP4 低延迟转码** | 独立 FFmpeg 输出 fMP4，WS 分片推送，`<video>` 原生播放 | 旧方案 JPEG 帧流只有 5–10fps 无声音，无法用于判断精彩瞬间 | 🟥 P0 |
| **1s 分片节奏**（`-frag_duration`） | 每片约 1s，30fps 推送 | 延迟与流畅的平衡点；片太长延迟高，片太碎开销大 | 🟧 P1 |
| **硬解降级链**（NVENC → CUDA 全 GPU → d3d11va 硬解 → 纯 CPU） | 逐级回退的编码/解码方案 | 保证在虚拟机、无 GPU、老驱动机器上**仍能预览** | 🟧 P1 |
| **per-room 画质分级**（原画/高清/标清/流畅） | 每路独立设定预览画质 | 已对齐、不需持续观看的房间可降为流畅（640×360）**省内存与 CPU**，是多房场景的刚需 | 🟥 P0 |
| **压力自动降级**（≥3 路→≤854×480@20fps；≥4 路→≤640×360@15fps） | 按路数自动降规格 | 12 路并发时前端解码能力是硬瓶颈，不降级就整体卡死 | 🟥 P0 |
| **watchdog 自动重连**（前端 10s / 后端 15s 无数据） | 检测卡流并重启通道 | 长时间挂机场景**必然**遇到假死，无 watchdog 则画面永久冻住 | 🟧 P1 |
| **预览时钟周期重标定**（60s） | 周期性重新锚定时钟 | 预览时钟漂移会直接**污染切片精度**（标记点与画面不符） | 🟥 P0 |
| **录制文件回看**（DVR 缓冲耗尽 → 切本地录制文件） | 拖出 MSE 缓冲后改播本地录制段 | 直播缓冲有限；没有它则"想回看 5 分钟前"做不到 | 🟧 P1 |
| **播放器基础交互**（seek / 播放暂停 / 静音 / 画质切换） | 基础播控 | 预览可用性的下限 | 🟥 P0 |
| **背压控制**（`mse_backpressure`） | 前端消费慢时反馈给后端限流 | 慢客户端会拖垮后端并影响其他房间，是"一个房间卡死全部"的经典故障 | 🟧 P1 |
| **init 段补发**（`request_mse_init` / `replay_init`） | 竞态时补发 fMP4 init 段 | 缺 init 段视频直接黑屏，且是随机复现的难查问题 | 🟧 P1 |
| **沉浸式全屏预览** | 单路全屏观看 | 监看体验；不影响核心链路 | 🟨 P2 |

## 4. 捕获层 C：共享进样（⚠️ 争议功能）

| 功能 | 做什么 | 为什么存在 / 争议点 | 等级 |
| :--- | :--- | :--- | :--- |
| **单上游扇出**（`SharedRoomIngest`） | 同一房间"录制+预览"只拉一次流，扇出给两个 sink | 理论收益：省一半上行带宽与 CPU，解决"双凤尾"重复重连。**但**：预览编码参数配置在单个 ingest 实例上，**无法 per-room 差异化**，与"已对齐房间降为流畅模式"的刚需直接冲突 | ⬜ 存疑 |
| **`replace_upstream`**（保留下游换源） | 换 CDN 时不重建下游 | 若启用共享进样，这是避免"换源即打断录制"的必要能力 | 🟧 P1（条件性） |
| **队列溢出保护 / `drop_oldest`** | 下游消费慢时丢最旧帧 | 防止单下游阻塞整条管道 | 🟧 P1（条件性） |
| **分段录制 + manifest**（`-f segment`） | 长录制切分成多段 | 若启用则便于崩溃恢复；但独立录制路径已用单文件方案 | 🟨 P2（条件性） |

> **事实核对**：`lsc/config.py:210` 默认 `shared_ingest_enabled = True`；仓库内 `python-backend/settings.json` 为 `true`，而根目录 `lsc_config.json` 为 `false`。**两套配置口径不一致**，实际生效行为需明确。项目历史决策倾向"维持独立双进程（关闭共享进样）"——若成立，本节 4 项功能即为**架构性弃用但未清理**的死代码。

## 5. 处理层 A：时间线与标记（切片精度核心）

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **墙钟标记**（`set_mark_in` / `set_mark_out`） | 记录用户按 i/o 时刻的单调时钟值 | 用户按的是"看到的那一刻"，必须能换算回文件位置 | 🟥 P0 |
| **三轴时间换算**（`TimelineContext`：公共轴 ↔ 预览轴 ↔ 录制轴） | 三个时间坐标系双向转换 | 预览流有单独延迟、每路录制起点不同，**没有这层换算，切片必然偏几秒** | 🟥 P0 |
| **公共时间轴对齐** | 多房在同一坐标系下显示播放头/切片 | 多视角同时标记的前提；零点取最早录制起点（避免负时间） | 🟥 P0 |
| **时间线快照**（`create_clip_snapshot`） | 固化某时刻的时间线状态 | 防止后续状态变化导致已标记切片漂移 | 🟨 P2 |
| **波形显示** | 时间线上绘制音频波形 | 找高光/校验对齐的辅助视觉 | 🟨 P2 |
| **DVR 缓冲范围标注** | 标出可回看的边界 | 让用户知道"还能拖多远" | 🟨 P2 |
| **磁吸吸附 / Alt 精确模式** | 拖标记时吸附到关键点，Alt 关闭吸附 | 精修工效；不吸附则手抖偏移 | 🟨 P2 |
| **播放速率控制**（0.5/1/1.5/2×） | 变速浏览 | 快速浏览长录制 | 🟨 P2 |
| **时间线回放窗口设置**（关/2/5/10 分钟） | 限制时间线保留时长 | 超长挂机时回放窗口过长会拖慢前端 | 🟨 P2 |

## 6. 处理层 B：多视角音频对齐

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **8s PCM 采集**（Web Audio / AudioWorklet，16kHz mono） | 从各房预览流抓取音频样本 | 对齐的输入数据源；不采集就无从计算 | 🟧 P1 |
| **FFT 互相关 + 抛物线插值** | 计算音频间时间差，亚毫秒精度 | **多视角同步导出的唯一技术支点**；没有它，多路切片各偏各的 | 🟥 P0 |
| **置信度防线**（相似度 < 0.3 判定不相关 → 降级 0 偏移） | 拒绝低质量对齐结果 | 房间内容无关时仍会算出一个假偏移，**误对齐比不对齐更糟**（静默产生错误成品） | 🟥 P0 |
| **双特征 fallback**（波形相关低时改用瞬态包络） | 换一种音频特征重估 | 纯音乐/单声道解说场景下波形互相关失效 | 🟧 P1 |
| **全局加权最小二乘**（多房构图 + `lstsq`） | 两两相关构图后估计每房相对基准的偏移 | 3 房以上时链式两两对齐会累积误差，需全局最优解 | 🟧 P1 |
| **最慢流为基准** | 公共轴零点/基准取进度最慢的房间 | 保证公共轴不出现负时间（无法表达的"过去"） | 🟥 P0 |
| **手动设置偏移**（`set_content_offset`） | 人工覆盖自动结果 | 自动算法失效时的最后兜底 | 🟨 P2 |

## 7. 处理层 C：AI 持续高光分析（Valorant）

| 功能 | 做什么 | 为什么必须存在 | 等级 |
| :--- | :--- | :--- | :--- |
| **持续分析**（`start_continuous_analysis`） | 录制过程中实时扫描高光 | **核心差异化卖点**；事后分析要等录完，错过实时剪辑窗口 | 🟥 P0 |
| **单房一次性分析**（`start_analysis`） | 对已有录制文件整体扫描 | 补录/重分析场景，也是持续分析的基线能力 | 🟧 P1 |
| **纯 OCR 回合检测**（顶部计分板 + 回合计时器 + 中央横幅） | 1fps 双区域扫描识别回合边界 | 不依赖游戏内 API，**对任意直播间画面通用**；这是能落地的前提 | 🟥 P0 |
| **回合状态机**（`OcrRoundFSM`：WAIT→PREP→COMBAT→SETTLE） | 用交战钟递减 streak / 满钟 / 结算倒计时判边界 | 单帧 OCR 不可靠，只有时序状态机能抗误识别（漏检/重播/挂机） | 🟥 P0 |
| **边界精修**（`refine_valorant_round_boundaries` 密扫） | 对候选边界做加密采样精修 | 1fps 粗扫的边界误差可达 ±1s，**切偏 1s 可能切掉一血** | 🟧 P1 |
| **主房分析 → 副房映射** | 只分析主房录制文件，副房按时间差映射入列 | 分析是 CPU/GPU 密集型；4 房全分析成本 ×4，映射即可 | 🟧 P1 |
| **pending 待确认机制** + 精修/确认/取消（`begin_refine_clip`/`confirm_highlight_clip`/`cancel_refine_clip`） | AI 结果默认待确认，人工确认后才可导出 | **防误检污染成品**；AI 必然有误判，缺这道闸门则成品不可信 | 🟥 P0 |
| **DirectML 加速 + CPU 降级** | 有 GPU 用 DirectML，无 GPU 退 CPU | 虚拟机/无 GPU 机器仍可用（仅变慢）；不降级则半数机器不可用 | 🟧 P1 |
| **相位调度 / 功耗控制 / 预览压力降级** | 按预览路数与系统压力调节 OCR 采样间隔与预算 | 分析必须**与录制共存**；抢占资源会导致录制掉帧甚至断流 | 🟥 P0 |
| **结果落盘与续跑**（sidecar + finalization checkpoint） | 分析结果持久化、中断后可恢复 | 现状：`_analysis_jobs` 内存 TTL 5 分钟，重启即丢；挂机数小时后丢结果不可接受 | 🟧 P1 |
| **观战/赛事 profile**（`valorant_observer_scoreboard` + broadcast 保护） | 适配转播画面（观战比分板、回放保护） | 赛事转播是目标用户群之一，与第一视角画面结构不同 | 🟨 P2 |
| **音频能量峰值检测 fallback**（`detect_audio_energy_peaks` / `detect_rounds_by_audio_rhythm`） | 用音量节奏兜底切分 | OCR 不可用（画面无/改动）时的备选 | ⬜ 存疑 |
| **场景检测 fallback**（非 Valorant 游戏） | 通用场景变化检测 | 宣称支持其他游戏，但**是否有真实用户使用需验证** | ⬜ 存疑 |

## 8. 产出层：切片导出与剪映衔接

| 功能 | 做什么 | 为什么必须存在 | 等级 |
