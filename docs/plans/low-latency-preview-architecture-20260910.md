# 低延迟预览架构方案对比（2026-09-10）

## 1. 背景

用户在实际使用中观察到「时间线/预览相对直播存在延迟」。前几轮已修复：
- 预览时钟（`recording_to_preview_delta`）由一次性标定改为 60s 周期重标定
- CPU 回退路径补 `-tune zerolatency`、muxer 加 `-flush_packets 1`

本文评估**是否引入更低延迟的预览链路**（架构级），并给出方案对比与推荐路线。

---

## 2. 现状架构

系统支持两种预览/录制架构（CLAUDE.md §7.3），由 `shared_ingest_enabled` 控制：

### 2.1 独立双进程（默认，`shared_ingest_enabled=False`）

```
直播 CDN
  ├── 连接1 → FFmpeg A (StreamCapture) → 录制文件（磁盘）
  └── 连接2 → FFmpeg B (MseStreamer)   → fMP4 → WebSocket → MSE
```

两条**独立 CDN 连接**。录制多为 `-c copy` 直拷；预览转码为 fMP4。

### 2.2 共享进样（可选，`shared_ingest_enabled=True`）

```
直播 CDN
  └── 单个远端上游 FFmpeg (SharedRoomIngest)
        ├── sink1: -c copy        → 录制文件
        └── sink2: libx264        → fMP4 → WebSocket → MSE
```

- 录制 sink 与预览 sink **互相解耦**（一方故障不停另一方），由 `IngestSupervisor` 统一恢复
- 预览与录制**同源** → 时间线天然一致，无跨连接漂移

> [!IMPORTANT]
> **该模式默认关闭是维护者的有意决策（2026-09-10 确认，不要轻易翻案）**：
>
> 共享进样的预览编码参数是配置在**单个 ingest 实例**上的
> （`_configure_shared_preview_quality()` → `shared_ingest.configure_preview(...)`，一处一参），
> 因此**无法按房间差异化预览画质**。而多直播间场景的核心节流手段恰恰是：
> 把「已对齐、不需要持续观看」的房间预览调为**流畅模式**（640×360 / 600–800k），
> 以降低内存与 CPU 占用——多房对齐后再开录制的开销本身已非常巨大。
>
> 独立双流模式通过 **per-room 的 `room.preview_quality`** 支持这种差异化降质
> （`_compute_preview_quality_params(data)` 按房间取值），这是共享进样给不了的。

### 2.3 共用的 URL 解析

两种模式都走 `lsc.platforms.resolver.resolve_stream_v2`，遵循各平台
`PlatformCapabilities.preferred_protocols`：

| 平台 | 协议偏好 |
|---|---|
| bilibili / huya | `("flv", "hls")` —— **FLV 优先** |
| kuaishou / weibo 等 | `("hls", "flv")` —— **HLS 优先** |

## 3. 延迟预算（逐层拆解）

| 层 | FLV 源 | HLS 源 | 说明 |
|---|---|---|---|
| 平台解析 | 0.2–1s | 0.2–1s | URL 解析 + 候选健康探测（有缓存） |
| **源协议** | **0.5–2s** | **2–6s** | **决定性变量**：FLV 长连接 vs HLS 分片粒度 |
| FFmpeg 转码 | 0.3–1s | 0.3–1s | `-g 30`（1s GOP）+ `-tune ll` / `-tune zerolatency` |
| fMP4 mux | <0.1s | <0.1s | `-flush_packets 1`，`-frag_duration 1000ms` |
| WebSocket | 0.05–0.2s | 同 | 本机回环 |
| MSE 缓冲 | 0.5–2s | 同 | 前端 `_replayBufferSeconds` trim |
| **合计** | **≈1.5–4s** | **≈3–9s** | |

**关键结论**：

1. **源协议是最大变量**。FLV 优先的平台（bilibili/huya）预览已接近链路下限；
   HLS 优先的平台（kuaishou 等）才是低延迟优化的主要对象。
2. 转码/mux/传输层已在前几轮压到接近极限，继续压收益 < 1s 且伴随稳定性风险。
3. 前端的 MSE 缓冲由用户设置的回放时长控制，属可调项而非缺陷。

## 4. 方案对比

| 方案 | 预期延迟 | 稳定性 | 工作量 | 适用场景 |
|---|---|---|---|---|
| **A. 维持现状**（独立双进程 + 协议偏好） | FLV 1.5–4s / HLS 3–9s | 高 | 0 | 基线 |
| ~~B. 开启共享进样~~ | 同 A，但预览与录制**同源零漂移** | — | — | **已排除**：丧失 per-room 画质分级（见 §2.2） |
| **C. 预览强制优先 FLV** | HLS 平台 **−2 ~ −4s** | 中（需 HLS 兜底） | 小 | HLS 优先平台 |
| **D. WebRTC / WHEP 拉流** | **0.2–0.5s** | 低（实现复杂） | 大 | 确有 1s 级需求 |
| **E. LL-HLS / CMAF 低延迟分片** | −1 ~ −2s | 中 | 中 | **依赖源站支持**，本项目不可控 |

### 方案 B：开启共享进样 —— **已排除（不再评估）**

理论收益是"预览与录制同源 → 时间线零漂移 + 少一路 CDN 连接"。但维护者实测确认：

1. 预览编码参数挂在**单个 ingest 实例**上，**无法 per-room 差异化**；
2. 多房场景会失去"已对齐房间降为流畅模式"这一关键节流手段；
3. 多直播间对齐 + 录制本身开销巨大，共享上游会进一步放大。

**替代方案**：跨连接漂移问题已在**独立双流架构内**通过「预览时钟 60s 周期重标定」
解决（见 CHANGELOG v1.0.12），无需为此牺牲按房间的画质分级。

### 方案 C：预览强制优先 FLV

- **现状**：协议偏好已按平台声明，但 HLS 优先平台上预览会直接走 HLS。
- **做法**：预览解析时对 HLS 优先平台**追加 FLV 候选**，取不到再回退 HLS。
- **风险**：部分平台/房间可能**没有 FLV 源** → 必须保留 HLS 兜底与超时。
- **收益**：HLS 平台预览延迟可降 2–4s（最大单项收益）。

### 方案 D：WebRTC（仅结论）

延迟可到 0.2–0.5s，但需要：WHEP/信令、ICE、H264 打包、前端 `RTCPeerConnection` 渲染路径改造，
且与现有 MSE/录制轴的映射需要重建。**不建议在 v1 引入**。

### 方案 E：LL-HLS（仅结论）

延迟取决于**源站是否提供 LL-HLS（#EXT-X-PART）**，本项目无法单方面启用；排除。

---

## 5. 推荐路线

1. **不动架构**：维持独立双进程。**per-room 预览画质分级是刚需**（见 §2.2），
   共享进样（方案 B）已排除。
2. **短期（小改，收益最大）**：实施 **方案 C**（预览优先 FLV + HLS 兜底）。
   对"流畅模式"房间同样有效——低分辨率走 FLV 直拉，CPU 与延迟双降。
3. **长期**：确有 1s 级需求再评估 **方案 D**。
4. **原则**：漂移/一致性类问题优先在现有架构内解决（如已完成的预览时钟周期重标定），
   不为低延迟牺牲多房差异化节流能力。

---

## 6. 附带发现（建议一并修）

**预览画质基线不一致**：

- `MseStreamer`（独立模式）**硬编码 `-crf 28`**
- `SharedRoomIngest`（共享模式）使用可配 `shared_ingest_preview_crf`（默认 **23**）

同一直播在两种模式下预览画质不同。`docs/SUBSYSTEM_ANALYSIS.md:135` 已记录该问题并标注"待核实前端无感知"。

**建议**：统一为配置项（如 `preview_crf`，默认 23），两种模式共用，消除双基线。
