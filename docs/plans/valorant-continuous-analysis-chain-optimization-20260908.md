# Valorant 持续分析整条链路优化计划

> **版本**：v1.0 · 2026-09-08  
> **适用范围**：Valorant 持续分析、录制后分析、官方赛事/解说分支、模型训练与前端状态提示  
> **关联文档**：
> - `docs/plans/valorant-broadcast-phase1-architecture-and-ux.md`
> - `docs/plans/valorant-broadcast-phase2-dataset-and-vision-enhancement.md`
> - `scripts/valorant_vision/manifest_schema.md`

## 1. 计划目的

本计划把“速度”和“精度”拆成可观测、可验收的链路指标，解决以下问题：

1. 视觉模型单独很快，但 FFmpeg、OCR、调度和候选审计导致端到端滞后；
2. 官方赛事画面与第一视角画面分布不同，不能共用同一套标签语义和验证标准；
3. 粗标数据数量大但存在噪声，人工标签数量少，直接混合重训会造成模型遗忘；
4. 单帧高置信度不等于真实边界证据，`result`、`replay` 和 `non_game` 转场仍可能误判；
5. 前端需要同时告诉用户“处理是否跟得上”和“结果是否足够可信”，不能只显示一个 FPS。

本计划的最终目标是：

```text
实时性：端到端净覆盖速度稳定 ≥ 1.0x，滞后不持续增长
准确性：官方解说候选以 OCR + 视觉 + 时序证据定稿，低证据结果保持 pending
可解释性：前端展示实际吞吐、滞后、模型设备、待复核数量和证据状态
可回滚：任何候选模型或策略都不直接覆盖生产版本
```

## 3. 链路总览

```text
录制文件 / 直播流
        │
        ▼
FFmpeg 增量抽帧与时间戳
        │
        ├── 顶部计分板 / 回合计时器 OCR（准确性主锚点，默认 1 FPS）
        ├── 中央横幅 OCR（按候选与压力惰性触发）
        └── 视觉模型
              ├── POV：整帧模型 + POV OCR，禁止 Replay
              └── Broadcast：整帧 + 顶部 HUD 融合，允许 Replay
        │
        ▼
连续帧时序稳定器
        │
        ▼
官方解说安全审计 / POV 回合 FSM
        │
        ├── evidence sufficient → confirmed
        ├── evidence incomplete → pending
        └── conflict / model unavailable → review required
        │
        ▼
持续分析状态、切片列表、人工确认、导出
```

## 4. 阶段 0：建立可复现实验基线

### 目标

冻结当前生产模型和数据口径，确保后续优化可以比较，避免把训练集内分数误当成泛化能力。

### 工作项

1. 为每个候选模型保存独立目录，不覆盖 `lsc/analyzer/models/valorant_phase_v1.onnx`；
2. 每次训练保存：模型 SHA-256、数据清单 SHA-256、训练样本数、验证样本数、来源比例、随机种子；
3. 统一记录三类评估：
   - 旧官方解说验证集：检测旧能力是否回退；
   - NS vs G2 完整 897 帧：检测新官方解说域泛化；
   - 独立测试视频：最终发布前盲测，不参与阈值选择；
4. 所有验证按完整 `video_id/session_id` 分组，禁止相邻帧跨 train/val/test；
5. 记录候选模型是否使用：顶部融合、类别阈值、时序修正和 OCR 证据。

### 完成标准

- 任意候选模型都可以由清单和参数重新生成；
- 训练、校准、最终测试的样本边界明确；
- 生产模型有可恢复备份，候选失败不会影响生产。

## 5. 阶段 1：速度与质量遥测

### 目标

让用户看到真实端到端状态，而不是把模型 FPS 当成整条分析链路速度。

### 5.1 后端指标

在 `continuous_analysis_status` 中统一维护以下字段：

| 字段 | 计算方式 | 用途 |
|---|---|---|
| `sample_fps` | 本轮抽帧采样频率 | 说明实际分析密度，默认 1.0 |
| `model_infer_fps` | 模型处理帧数 ÷ 模型耗时 | 说明视觉模型容量 |
| `model_infer_ms_p50/p90` | 模型批次延迟分位数 | 识别 CPU/GPU 或批量异常 |
| `scan_wall_sec` | 本轮完整墙钟耗时 | 计算端到端吞吐 |
| `gross_scan_throughput` | 扫描媒体秒数 ÷ 墙钟耗时 | 说明粗扫成本 |
| `net_coverage_throughput` | 新增覆盖媒体秒数 ÷ 墙钟耗时 | 判断是否追得上录制 |
| `analysis_lag_sec` | 已录制时长 − 已分析时长 | 当前落后量 |
| `analysis_lag_p90` | 最近滞后样本 P90 | 判断持续落后，不受单次尖峰干扰 |
| `audit_queue_depth` | 待审计候选数量 | 判断后台审计是否积压 |
| `pending_review_count` | 待人工/证据不足数量 | 质量风险提示 |
| `model_version/provider` | 模型版本和实际执行设备 | 追踪运行环境 |

后端已有 `gross_scan_throughput`、`net_coverage_throughput`、`analysis_lag_*` 等字段，应优先补齐模型推理计时并保持字段含义不变。

### 5.2 前端提示

在 `lsc-electron/src/components/AnalysisProgress.tsx` 的详情区域显示：

```text
状态：实时跟进 / 追赶中 / 待复核 / 异常
实际覆盖速度：1.24x
采样频率：1.0 帧/秒
视觉推理：49.8 帧/秒
推理设备：CPU / DirectML / CUDA
当前滞后：8 秒，P90：15 秒
待审计：3 个，待复核：2 个
```

显示语义：

- `net_coverage_throughput >= 1.0x` 且滞后不增长：绿色“跟得上”；
- `< 1.0x` 且滞后持续增加：黄色“正在落后”；
- 模型不可用、审计冲突或证据不足：红色/黄色“需复核”；
- 直播持续录制时不能把进度显示成“100%完成”。

### 完成标准

- 用户能区分模型速度、抽帧速度和端到端覆盖速度；
- 速度降级时明确显示原因；
- 质量风险不被速度数字掩盖；
- 增加后端状态载荷、前端状态推导和测试覆盖。

## 6. 阶段 2：抽帧、OCR 与调度性能优化

### 目标

把 CPU 时间优先分配给真正影响边界的证据，保持准确性关键采样不降级。

### 工作项

1. **GPU provider 预检**
   - 启动时明确探测 `DmlExecutionProvider` / `CUDAExecutionProvider`；
   - 日志必须记录“请求设备、实际设备、回退原因”；
   - GPU 不可用时不伪装成 GPU，进入 CPU 慢速提示；
   - 运行时不能因为 GPU 探测阻塞编排线程。

2. **保持 1 FPS 顶部锚点**
   - 顶部计分板和回合计时器是边界证据，不能简单降到 0.25 FPS；
   - 中央横幅 OCR 按候选、类别变化、低置信度和 backlog 自适应触发；
   - 继续跳过无需 OCR 的 Replay/unknown 帧，但必须记录跳过原因。

3. **减少 FFmpeg 进程启动成本**
   - 评估持续解码管道或按窗口复用解码器；
   - 保留现有取消、超时和断点恢复机制；
   - 不允许为了复用进程而丢失 PTS、重复扫描或破坏窗口边界。

4. **批量视觉推理**
   - 默认 batch size 16–32；
   - 完整画面与顶部 HUD 融合在同一审计批次内完成；
   - 复用已加载的 ONNX session；
   - 记录批次延迟和实际吞吐，避免用单次 warm-up 结果当生产速度。

5. **并发与 backlog 策略**
   - backlog ≤30 秒：正常 OCR + 有界审计；
   - 30–60 秒：减少非必要中央 OCR，保持顶部锚点；
   - >60 秒：粗扫优先、审计配额有界；
   - 任何压力模式都不能关闭官方解说的最终证据门禁；
   - 审计 worker 与粗扫 worker 解耦，避免 OCR 阻塞编排线程。

### 完成标准

- 1 小时官方解说回放中，端到端净覆盖速度连续 5 个窗口 ≥1.0x；
- backlog 不持续增长；
- 单回合审计 P90 耗时和 OCR 失败率有记录；
- CPU/GPU 两种环境都能安全运行；
- 取消、超时、重试和断点恢复测试通过。

## 7. 阶段 3：官方解说视觉与时序决策优化

### 目标

提升官方解说 `result/replay/non_game` 的边界可靠性，同时完全隔离 POV 语义。

### 7.1 输入策略

当前试验结果支持：

```text
Broadcast fused probability = 0.70 × full_frame + 0.30 × top_HUD
```

顶部区域包含赛事比分、计时器和导播 HUD；中央区域和右下角单独裁剪在当前实验中反而降低整体指标，暂不默认加入。

实现要求：

- `predict_broadcast_batch()` 只由 broadcast 审计调用；
- POV 路径继续使用原有整帧/纯 OCR 逻辑；
- 融合配置写入模型元数据，缺失时回退整帧推理；
- 生产模型未配置融合时不得隐式改变其行为。

### 7.2 时序稳定器

在 `lsc/analyzer/valorant_broadcast.py` 中使用保守规则：

```text
前一帧标签 == 后一帧标签 != 当前帧
且当前帧为 unknown 或低证据
→ 使用邻帧一致标签
```

约束：

- 绝不覆盖高置信度当前标签；
- 单帧 Replay/Result 不能直接触发边界截断；
- 时序修正必须兼容跨增量窗口缓存；
- Replay 只在 broadcast 分支有效；
- 时序修正后仍须经过 `audit_broadcast_phase_sequence` 和证据印章。

### 7.3 类别阈值

类别阈值只能用于“是否接受该类别证据”，不能直接伪造另一类别：

- Replay 暂定稳定阈值：0.77；
- Result 暂定稳定阈值：0.60；
- 低于阈值：`unknown/pending`，不自动当作 combat；
- 阈值必须在独立校准集上选择，并在另一段视频上复核。

### 7.4 结构证据

官方解说最终定稿优先使用：

1. Observer 比分跳变；
2. 顶部计时器连续变化或冻结；
3. 视觉模型连续 Replay/Result/Non-game 证据；
4. OCR 回合顺序和时长约束；
5. 人工确认或 pending 保留。

证据冲突时的策略是“延迟定稿”，而不是降低阈值猜测。

### 完成标准

- NS vs G2 897 帧上融合 + 时序方案保持或提升指标；
- 单帧噪声不再造成赛事回合过早截断；
- Replay/Result 必须有连续证据；
- POV 不出现 Replay 标签；
- 相关纯函数和 broadcast 回归测试通过。

## 8. 阶段 4：数据集与训练优化

### 目标

让人工标签、粗标和独立验证各自承担正确职责，避免粗标噪声造成灾难性遗忘。

### 8.1 数据分层

| 数据类型 | 用途 | 训练权重 |
|---|---|---:|
| 已人工确认标签 | 主监督信号 | 1.0–2.0 |
| 粗标且置信度 ≥0.70 | 伪标签/域适应 | 0.30 |
| 粗标 0.55–0.70 | 低权重伪标签 | 0.15 |
| 粗标 <0.55 | 保留参与，但只给极低权重 | 0.05 |
| 独立完整验证视频 | 只验证，不训练 | 0 |

此前用户确认的 EDG 两个视频 1601 帧可以继续全部参与训练，但必须保留上述来源标记。

### 8.2 训练策略

1. 从现有 ONNX 权重微调，不从 ImageNet 重新初始化；
2. 旧官方解说数据全部保留，防止新视频域适应导致旧能力遗忘；
3. 使用旧模型蒸馏约束，尤其保护原有 `combat/replay` 决策边界；
4. 对 `result` 误报、`non_game` 漏报和 Replay 转场做 hard mining；
5. 训练集可使用完整新增数据，但验证集必须按视频/会话隔离；
6. 每轮训练至少比较：旧官方验证集、NS vs G2 验证集、独立盲测集。

### 8.3 数据扩充优先级

优先补充：

1. `result` 结算横幅与普通导播包装的对比样本；
2. `non_game` 演播室、广告、地图、选手镜头；
3. Replay 切入/切出前后 3–5 秒连续边界；
4. 买枪阶段与结算倒计时相邻画面；
5. 不同赛事包装、分辨率、画中画和语言字幕。

### 完成标准

- 新训练不会降低旧验证集超过预设回退阈值；
- `result` 精确率、`non_game` 召回率有明确改善；
- 伪标签来源、人工来源和验证来源可追踪；
- 新增模型有候选目录和 SHA-256 元数据；
- 失败候选不覆盖生产模型。

## 9. 阶段 5：持续分析调度与证据门禁

### 目标

让速度压力只影响分析调度，不破坏边界安全。

### 工作项

1. 粗扫只推进覆盖游标和回合候选，不同步等待完整深审计；
2. 审计候选持久化到 `broadcast_pending_rounds`，支持重启恢复；
3. 审计 worker 按可用后视窗口和优先级消费，不因单个候选阻塞全部队列；
4. `pending` 可以在前端展示，但不得自动导出；
5. `vision_confirmed` 只有在起点和终点证据完整时才能进入自动导出门禁；
6. 模型不可用时 broadcast 安全拒绝或转人工复核，不回退为猜测；
7. `reason=none` 不得伪造 `broadcast_exclusion` 或 `precise`；
8. 收尾阶段必须补扫尾部未覆盖范围，不能用进度百分比代替 coverage 完成。

### 完成标准

- 首个粗候选可以及时显示为 pending；
- 审计完成后只做局部更新，不重置整个切片列表；
- 任意 worker 超时后，剩余候选仍可恢复；
- 自动导出只接受完整证据切片；
- 录制停止、重连、收尾和模型异常均有明确状态。

## 10. 阶段 6：速度与精度验收

### 10.1 发布门禁

沿用 `scripts/valorant_vision/eval_gates.py` 的基础门禁：

| 指标 | 最低要求 |
|---|---:|
| 五分类 Macro F1 | ≥ 0.9400 |
| Replay Recall | ≥ 0.9500 |
| Non-game Recall | ≥ 0.9500 |
| Buy Precision | ≥ 0.9700 |
| Result Precision | ≥ 0.9700 |

当前候选模型尚未全部通过上述门禁，因此只能作为候选或 shadow model。

### 10.2 持续分析端到端门禁

新增以下生产门禁：

| 指标 | 目标 |
|---|---:|
| 净覆盖速度 | 连续 5 个窗口 ≥ 1.0x |
| 滞后趋势 | 不持续增长 |
| 审计队列 | 不发生无界增长 |
| 单回合最终审计 P90 | ≤ 40 秒，按机器环境单独记录 |
| Replay/Result 单帧误截断 | 0 |
| 证据不足自动导出 | 0 |
| 边界误差 P95 | ≤ 0.8 秒 |

### 10.3 Shadow 运行

候选模型进入生产前，使用同一录制文件并行计算：

```text
生产模型结果 ─┐
              ├─ 比较切片边界、标签、证据状态和耗时
候选模型结果 ─┘
```

候选只有在旧域、新域和端到端速度均不出现明显回退时，才进入小范围启用。

## 11. 阶段 7：发布、回滚与运行安全

### 发布流程

1. 生成候选目录和元数据；
2. 完成 CPU/GPU 推理一致性检查；
3. 完成旧域、新域和盲测报告；
4. 先 shadow，再小范围启用；
5. 观察实时吞吐、滞后、待复核和误截断；
6. 明确记录当前生产模型版本和候选版本。

### 回滚条件

出现以下任一情况立即回滚：

- 净覆盖速度持续低于 1.0x 且 backlog 增长；
- Replay/Result 误截断增加；
- 模型 provider 回退且 CPU 负载影响录制/预览；
- 候选模型契约、SHA-256 或类别顺序校验失败；
- 自动导出出现无完整证据切片。

回滚只切换模型目录或配置，不删除原始录像、标注、清单和日志。

## 12. 需要用户确认的事项

当前可以继续自动推进，不需要立即决定；以下节点会明确需要你的判断：

1. **NS vs G2 897 帧是否转为训练数据**：一旦加入训练，它就不再是独立验证集，需要另外提供一段独立官方解说素材；
2. **候选启用范围**：是否先只在官方解说分支 shadow，保持第一视角完全不变；
3. **速度与精度取舍**：默认采用质量优先，宁可 pending 也不对证据不足的片段自动截断；
4. **新增素材优先级**：如果继续录制，优先提供包含完整 Replay/Result/Buy 转场的官方解说视频。
