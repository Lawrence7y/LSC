# 多平台直播稳定性总体架构规格

> 状态：提案  
> 日期：2026-08-09  
> 来源：[多平台直播适配与稳定性彻底治理实施计划](../../2026-08-09-multiplatform-adaptation-stability-implementation-plan.md)  
> 适用范围：LSC Electron 前端、Python Backend、lsc 核心业务层

---

## 1. 目的

本规格定义多平台直播接入的目标架构、职责边界和全局不变量。它不展开单个平台的私有解析细节，而是确保 B站、虎牙、快手、斗鱼、小红书、微博、直链和后续新增平台都通过同一条稳定链路工作。

核心结论：

    平台 URL
      -> 平台识别与能力声明
      -> 凭据上下文
      -> 候选流解析
      -> 真实媒体探测与评分
      -> 有效租约
      -> 房间级进样监督器
      -> 录制 Sink / 预览 Sink / 后续 Sink
      -> 分段产物、时间轴与导出

抖音现有稳定链路作为迁移对照组，必须先被基线化，再逐步接入统一运行时，不能在第一阶段直接替换。

---

## 2. 目标

1. 平台差异只存在于适配器、能力声明、凭据提供器和平台策略中。
2. 解析成功不等同于可用，候选流必须通过真实媒体探测后才能建立租约。
3. 同一房间默认只有一个受监督的远端上游连接，录制与预览作为独立下游消费。
4. 录制、预览和控制状态相互隔离，一个下游故障不能无条件拖垮其他下游。
5. URL 过期、CDN 拒绝、限流、凭据失效、网络抖动和主播下播具有不同恢复策略。
6. 录制产物在断流或进程退出后可以恢复、校验并继续被切片、OCR、对齐和导出消费。
7. 所有敏感 URL、Cookie、令牌和鉴权头在日志、事件和诊断包中默认脱敏。
8. 每个平台必须通过统一契约、故障注入、真实流验收和长稳测试后才能标记为稳定支持。

---

## 3. 非目标

1. 不绕过付费、私密、DRM、验证码或平台安全验证。
2. 不承诺第三方私有接口永久不变化。
3. 不在本轮增加推流、弹幕、多轨非线性编辑等新业务。
4. 不要求所有平台采用完全相同的解析实现。
5. 不通过无限重试掩盖凭据、协议或平台策略问题。

---

## 4. 分层职责

### 4.1 平台层

负责：

- 识别平台 URL 与房间标识。
- 声明平台能力和必要凭据。
- 获取直播状态、房间元数据和候选流集合。
- 返回结构化错误与平台建议，不启动 FFmpeg，不控制录制或预览。

### 4.2 媒体运行时层

负责：

- 规范化、去重、探测和选择候选流。
- 管理流租约、有效期、刷新和失效。
- 建立唯一上游连接并向多个下游分发。
- 处理超时、背压、重连、换线和熔断。
- 生成结构化健康状态与诊断事件。

### 4.3 应用协调层

负责：

- 管理房间、任务和用户意图。
- 启停录制、预览、分析和导出工作流。
- 将运行时状态转换为稳定的 WebSocket 和 HTTP 契约。
- 不包含平台专属的 Cookie、CDN 或状态码分支。

### 4.4 前端层

负责：

- 呈现真实健康状态和可操作错误。
- 收集授权范围内的凭据配置。
- 区分录制健康、预览健康和平台解析健康。
- 不解析平台网页，不持有完整敏感凭据。

---

## 5. 全局不变量

1. 一个 room_session_id 在任一时刻最多拥有一个主进样监督器。
2. 任一媒体连接必须来源于未过期且已通过探测的租约。
3. 候选流的探测必须使用与实际连接等价的请求头、代理和凭据上下文。
4. 预览 Sink 的启动、停止和失败不能改变 recording_requested。
5. 录制 Sink 的失败必须报告 degraded 或 failed，不能伪装为仍在正常录制。
6. 平台适配器不能持有跨请求可变状态；熔断、缓存和租约属于运行时服务。
7. 所有重试都有预算、退避和终止条件。
8. 所有输出文件都必须先写临时状态，经过关闭或校验后才能标记完成。
9. 旧版 stream_url 输入在兼容期内允许进入转换层，但不能绕过探测。
10. 任何日志或事件都不得包含可直接复用的完整签名 URL 或 Cookie。

---

## 6. 核心状态

房间运行态至少包含：

- IDLE：无活动会话。
- RESOLVING：解析房间与候选流。
- PROBING：验证候选流。
- CONNECTING：建立远端上游。
- STREAMING：上游可读，至少一个 Sink 可消费。
- DEGRADED：仍可提供部分能力，但存在丢帧、下游故障或候选降级。
- REFRESHING：租约即将过期或已判定失效，正在刷新。
- OFFLINE：平台确认未开播或已下播。
- AUTH_REQUIRED：凭据缺失或失效。
- BACKING_OFF：达到瞬时失败预算，等待退避。
- FAILED：已耗尽当前策略且需要人工或外部状态变化。
- STOPPING：有序关闭中。

状态变化必须由明确事件触发，并带有原因码、会话标识、尝试次数和时间戳。

---

## 7. 规格依赖

1. 平台契约与凭据规格定义平台层输出。
2. 解析、探测与租约规格定义可连接上游的产生方式。
3. 进样监督器规格定义运行时媒体生命周期。
4. 分段录制与时间轴规格定义持久化产物。
5. 平台迁移规格定义各平台接入上述契约的路径。
6. 可观测性与前端规格定义用户和运维如何理解系统状态。
7. 验证、灰度与发布规格定义何时允许启用和扩大覆盖。

核心规格按上述顺序实现；可观测性从第一批核心代码开始同步建设，不能等到最后补日志。

---

## 8. 兼容策略

- 保留现有 PlatformAdapter 与 StreamInfo 入口，新增转换器生成候选流结果。
- 保留现有 WebSocket 事件名，在载荷中增加 version、health 和 reason_code。
- 保留现有录制文件消费入口，通过清单聚合器向旧调用方提供逻辑单文件视图。
- 所有新链路受功能开关控制，可按平台、房间和功能单独启用。
- 抖音在其他平台达到门槛前保持对照模式；最后再进行同契约迁移。

---

## 9. 完成定义

满足以下全部条件，本总体规格才算完成：

1. 平台专属分支不再散落于 orchestrator.py、room_handler.py 和前端业务代码。
2. 所有支持平台返回统一候选流与结构化错误。
3. 录制和预览默认共享一个远端上游，且故障相互隔离。
4. 断流、URL 过期、403、429、凭据失效和下播均有可验证的状态转换。
5. 录制产物可恢复并通过后处理消费验证。
6. UI 能区分平台、进样、录制、预览和恢复状态。
7. 安全脱敏、自动化测试、真实流验收、长稳测试和回滚演练全部达标。

---

## 10. 待评审问题

1. 第一阶段是否允许使用本地中继进程作为单上游分发实现，还是直接引入进程内媒体管线。
2. 默认录制分段时长采用 60 秒还是按平台延迟特征动态调整。
3. 真实平台凭据由本机安全存储还是由独立凭据服务提供。
4. 稳定支持的最低长稳时长是否统一为 6 小时，还是按平台风险分级。
