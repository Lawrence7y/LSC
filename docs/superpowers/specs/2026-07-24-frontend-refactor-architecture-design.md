# LSC 前端重构架构设计

## 文档状态

- 日期：2026-07-24
- 状态：待用户评审
- 范围：Electron React 前端的布局、职责边界、状态归属与验证策略
- 不包含：生产代码修改、Python 后端协议修改、MSE/时间轴重写

## 1. 项目定位

LSC 是一个面向多直播间录制、同步切片和 AI 高光分析的桌面工作台。
它不是通用后台页面，也不是多轨非线性编辑器。前端需要同时协调：

1. 多直播间连接、预览和录制；
2. MSE 实时播放器与 Web Audio 对齐；
3. 公共时间轴、房间本地时间和录制文件时间映射；
4. 手动切片、AI 候选、确认、精修和导出；
5. 持续分析、导出队列、剪映草稿；
6. Electron 桌面生命周期、设置、依赖、日志和更新。

重构目标不是增加功能，而是让现有功能拥有清晰、稳定的前端归属。

## 2. 当前结构判断

### 2.1 已有可复用能力

- `RoomCard` 已承担单房间预览、连接、录制和错误反馈。
- `useRoomActions` 已提取单房间生命周期操作。
- `Timeline`、`ControlBar`、时间轴坐标工具已形成完整单轨交互。
- `ClipList` 已具备虚拟列表、确认、精修、导出、取消和失败恢复。
- `AnalysisProgress` 已能表达持续分析、停止和最终化阶段。
- `useExportProgressListeners`、`playheadStore`、时间轴 Worker 等性能优化已经存在。
- `appStore` 已提供房间、切片、设置、时间轴和持续分析的共享状态。

### 2.2 当前主要问题

- `Workbench/index.tsx` 同时承担页面布局、播放器协调、时间轴映射、分析、导出和大量弹窗状态。
- 顶部工具栏同时混入会话操作、分析状态和低频工具，层级不清。
- 右侧区域同时放置添加房间和切片列表，任务流归属不明确。
- 设置是 Drawer，但菜单选中态只依赖路由。
- WebSocket 类型表与真实广播事件并非完全一一对应，不能依赖一次性类型重写解决。
- 当前工作区存在未提交和未跟踪 WIP，重构必须以实际源码和测试为准。

## 3. 功能与前端需求

| 功能域 | 前端责任 | 必须保留的约束 |
|---|---|---|
| 房间管理 | 添加、连接、断开、删除、选择、批量操作 | 乐观状态、录制排队、危险操作确认 |
| MSE 预览 | 质量、静音、全屏、重连、错误和降级状态 | init/segment 缓存、单一播放器生命周期、最多四路预览 |
| 录制 | 单房间和批量开始/停止 | 持续分析运行时停止必须警告 |
| 音频对齐 | 捕获诊断、置信度、失败摘要和互斥状态 | 不混用 `preview_local`、`common`、`recording_local` |
| 单轨时间线 | 播放、拖拽、缩放、I/O、吸附、DVR、精修 | 拖拽时本地更新、松手 seek、现有快捷键不变 |
| 切片队列 | 待确认、精修、导出、取消、失败恢复 | `pending/refining` 不得直接导出 |
| AI 分析 | 模式选择、阶段、延迟、候选片段入列 | 无固定范围时不得显示伪 100%，不得自动导出 |
| 多房同步导出 | 为各目标房间建立独立任务 | 每个切片使用自己的边界，不隐式回退 |
| 剪映草稿 | 目录探测、生成、警告和打开结果 | 保留未对齐和待确认片段的显式语义 |
| 设置与运维 | 设置保存、依赖、Cookie、更新和日志 | 保留保存契约、路径安全和 Electron IPC |

## 4. 信息架构

工作台采用四个语义区域。

```text
┌────────────────────────────────────────────────────────────┐
│ 会话栏：添加房间 / 批量录制 / 批量停止 / 对齐 / 刷新       │
├───────────────────────────────────────┬────────────────────┤
│                                       │ 分析与切片队列      │
│ 房间区域：RoomCard 网格               │                    │
│                                       │ 待确认优先          │
│                                       │ 导出中其次          │
│                                       │ 已完成最后          │
├───────────────────────────────────────┤                    │
│ 编辑区：ControlBar + 单轨 Timeline    │                    │
└───────────────────────────────────────┴────────────────────┘
```

### 4.1 会话栏

主操作：

- 添加房间；
- 批量开始录制；
- 批量停止录制。

辅助操作：

- 全选；
- 音频对齐；
- 全部静音；
- 刷新房间；
- 排序。

房间数量作为会话标题信息显示，不与主操作争夺层级。排序属于辅助操作，不进入主操作行。

持续分析不再占据会话栏。其状态和下一步动作归入切片队列。

### 4.2 房间区域

- 继续使用现有 `RoomCard` 网格；
- 房间卡保持字段级 memo；
- 不让布局组件订阅或复制 MSE 事件；
- 展开、全屏和预览控制继续由现有房间组件与页面协调。

### 4.3 编辑区

- 继续使用 `ControlBar` 和单轨 `Timeline`；
- 不拆分第二套时间轴模型；
- 公共时间轴、对齐、确认和精修仍由 `Workbench` 协调；
- 不改变拖拽、吸附、缩放、快捷键、DVR 和回直播行为。

### 4.4 切片队列

- `AnalysisProgress` 放在队列顶部；
- `ClipList` 统一命名为“切片队列”；
- 列表保持单列，不按状态拆成多个 Tab；
- 第一阶段保持当前切片输入顺序，不暗中改变选择、虚拟列表和任务定位语义；
- 队列顶部只提供“入列、待调、可导”等状态摘要；
- 如果后续确认需要按状态排序，必须另设带稳定 identity 的独立任务；
- 添加房间改用 Modal，避免长期占用队列宽度。

## 5. 代码职责边界

### 5.1 `Workbench`

继续负责：

- 四区页面编排；
- WebSocket 订阅装配；
- MSE/Web Audio 对齐协调；
- 三轴时间映射；
- 时间轴、确认和精修联动；
- 页面级 Modal 和选中状态。

不再直接实现：

- 批量房间录制、停止和静音的重复流程；
- 导出提交、导出确认和剪映草稿会话的低耦合流程。

### 5.2 `useRoomBatchActions`

只负责：

- 批量开始录制；
- 批量停止录制；
- 对启用预览的房间批量静音。

要求：

- 回调执行时读取最新 store；
- 保留现有过滤条件、确认文案和乐观状态；
- 不接管音频对齐和房间卡渲染。

### 5.3 `useClipWorkflow`

只负责：

- 单个和批量导出提交；
- 导出确认弹窗；
- 剪映草稿生成会话。

要求：

- 每个切片使用自身边界；
- 通过注入的确认函数处理待确认片段；
- 不接管精修、拖拽、播放头或房间媒体控制；
- 不复制公共时间轴转换。

### 5.4 设置模块

设置仍在 Drawer 内。等工作台稳定后再按以下职责拆分：

- 设置加载与防抖保存；
- 依赖检测；
- Cookie 管理；
- 更新管理；
- 日志查看。

不新增独立设置路由，不改变后端设置契约。

## 6. 状态所有权

| 状态 | 所有者 |
|---|---|
| 房间、切片、连接、设置、时间轴上下文、持续分析状态 | `appStore` |
| 播放头高频位置 | `playheadStore` 与页面采样 |
| 添加房间、导出、分析、草稿等弹窗开关 | `Workbench` 页面状态 |
| 房间播放器实例和媒体缓存 | 现有 MSE/WebSocket 模块 |
| 切片虚拟列表滚动窗口 | `ClipList` |
| 设置分节选中态 | `Settings` |

重构不引入新的全局状态库，也不把一次性弹窗状态提升到 `appStore`。

## 7. WebSocket 与错误处理

- 不修改消息名、响应名、广播键或二进制 MSE 帧格式；
- 不在四个区域内重复注册同一事件；
- 断线时继续仅缓存安全读取请求，写操作显示提示；
- 保留 `send` 的布尔返回值，不将失败的写操作误判为已发送；
- 剪映草稿继续使用 `sendRequest`、`request_id` 和现有超时机制，不退回临时裸事件监听；
- 保留 `rooms_updated` 与 `room_updated` 合并逻辑；
- 保留 MSE watchdog、缓存 TTL 和按房间重试；
- 持续分析、录制、导出错误继续通过现有事件更新统一状态。

## 8. 视觉与交互规则

- 青色：主播放进度和播放头；
- 绿色：入点；
- 红色：出点；
- 蓝色：已确认切片和选择范围；
- 橙色：待确认 AI 候选；
- 单轨时间线的视觉层级保持不变；
- 无固定分析范围时使用“分析中 / 已跟进至”，不显示误导性的完成百分比；
- 危险操作必须有明确动作名称，不能只使用“确定”；
- 继续使用现有 CSS token，不做全仓库内联样式清扫。

## 9. 响应式与可访问性

- Electron 桌面验收尺寸以 `1360x800` 和 `1520x920` 为主；
- 浏览器模式可附加验证 `1280px`，但不能替代 Electron 最小尺寸验收；
- 宽屏保持房间区、编辑区和右侧队列同时可见；
- 窄屏浏览器模式下右侧队列移到房间区下方，并限制最大高度；
- Settings 必须按 `520px` Drawer 容器宽度设计，不能只依赖全窗口媒体查询；
- 主要操作按钮保留文字或 Tooltip；
- Modal 初始焦点落在首个可操作控件；
- 房间选中、录制、错误、待确认状态不能只依赖颜色表达；
- 保留现有键盘快捷键，不占用已有时间轴按键。

## 10. 非目标

- 不实现三轨、多轨或非线性编辑器；
- 不重写 Timeline、MSE、Web Audio 或坐标转换；
- 不修改 Python WebSocket 协议；
- 不新增前端依赖或第二套全局状态；
- 不一次性重构整个 Settings；
- 不覆盖或提交用户现有未提交修改；
- 不把现有未跟踪 WIP 文档视为已批准实现。

## 11. 实施顺序

1. 冻结基线和交互验收清单；
2. 先提供本地浏览器原型或截图，确认四区层级、会话栏内容和 Settings 导航；
3. 完成四区布局和设置抽屉选中态；
4. 提取批量房间操作；
5. 提取导出与草稿工作流；
6. 在性能数据支持下整理 selectors/view-model；
7. 最后拆分设置模块和收敛视觉 token；
8. 每阶段独立通过类型、守卫和手工验证。

## 12. 设计验收标准

- 用户能从“添加房间”顺畅完成“录制—对齐—切片—确认—导出”；
- 分析产生的候选片段在右侧同一队列完成确认和导出；
- 单轨时间线全部交互保持不变；
- MSE、音频对齐、WebSocket 和导出协议没有变化；
- `Workbench` 仍是协调层，但低耦合批量和导出流程不再内联；
- 设置 Drawer 的菜单状态正确；
- 窄屏下不出现不可访问的横向内容；
- 所有现有前端稳定性守卫继续通过。
