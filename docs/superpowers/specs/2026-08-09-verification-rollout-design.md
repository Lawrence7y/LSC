# 多平台稳定性验证、灰度与发布设计规格

> 状态：提案  
> 日期：2026-08-09  
> 上游规格：本系列全部多平台稳定性规格  
> 主要范围：自动化测试、真实平台验证、发布开关、监控和回滚

---

## 1. 目的

定义从代码完成到平台标记为稳定支持之间的证据门槛，确保“能够解析一次”不会被误认为“能够稳定录制、预览和完成后处理”。

---

## 2. 验证层级

### 2.1 静态与单元测试

- 类型检查、lint 和现有测试基线。
- 平台模型、错误分类、评分、租约和状态机单元测试。
- 凭据脱敏与路径安全测试。
- 时间轴和清单属性测试。

### 2.2 契约测试

- 所有平台运行同一适配器契约。
- 所有 Sink 运行同一生命周期契约。
- WebSocket 与 HTTP 运行兼容性契约。
- 所有错误码有稳定类别和用户提示。

### 2.3 本地集成与故障注入

使用可控假 CDN 和媒体样本模拟真实故障，不依赖第三方平台稳定性。

### 2.4 真实平台验收

使用授权账号和公开直播验证解析、探测、录制、预览、恢复和导出。

### 2.5 长稳与灰度

在内部和白名单环境进行长时间运行，满足指标后逐级扩大。

---

## 3. 假 CDN 故障矩阵

本地测试服务必须支持：

| 场景 | 预期行为 |
|---|---|
| 正常 FLV/HLS | 探测、进样、录制和预览成功 |
| 302 多跳 | 在安全限制内跟随并记录 |
| 403/410 | 租约失效并重新解析 |
| 429 + Retry-After | 按平台级预算退避 |
| 5xx 间歇失败 | 有限重试后换候选 |
| 慢首包 | 候选降分或超时 |
| 中途断流 | 单一恢复周期，录制产生可解释 gap |
| 静默但连接未断 | 根据无进度超时恢复 |
| 无音轨 | 按业务策略降级或换候选 |
| 坏容器 | 探测拒绝 |
| 时间戳跳变或归零 | 切段并保持逻辑时间轴 |
| 编码参数变化 | 切段、重置预览解码 |
| URL 定时过期 | 主动刷新或失效后换租约 |
| 慢预览消费者 | 丢弃预览旧帧，不阻塞录制 |
| 磁盘写满 | 录制安全失败，预览按策略继续 |

故障场景必须可重复、可指定随机种子，并在 CI 中保留失败诊断。

---

## 4. 自动化测试矩阵

每个支持平台至少覆盖：

- 未开播。
- 正常匿名解析。
- 正常凭据解析（适用时）。
- 凭据缺失、过期和拒绝。
- 多画质选择与降级。
- 多线路或多 CDN 选择。
- 首候选失败后切换。
- 录制单独运行。
- 预览单独运行。
- 录制与预览同时运行。
- 预览断开和重连。
- 上游断流和恢复。
- 正常停止与强制退出。
- 分段校验、恢复和导出。

没有真实平台测试的适配器最高只能达到 PREVIEW，不能仅凭夹具标记 STABLE。

---

## 5. 真实平台验收脚本

每次验收记录：

- 应用版本、提交、平台和支持等级。
- 网络环境与是否使用代理。
- 凭据状态，不记录明文。
- 房间与主播的脱敏标识。
- 期望画质和实际画质。
- 解析、首帧、开始录制、开始预览耗时。
- 重连、换线、缺口和分段校验结果。
- 停止、恢复和导出结果。

每个平台至少完成：

1. 15 分钟录制。
2. 15 分钟预览。
3. 30 分钟录制加预览并行。
4. 一次主动网络中断与恢复。
5. 一次应用重启后的产物恢复。
6. 一次跨分段切片、OCR 或音频对齐。
7. 一次最终导出并人工抽检。

---

## 6. 长稳门槛

进入 STABLE 前，平台在目标环境中至少满足：

- 连续 6 小时录制加预览运行，或经评审采用更高风险平台门槛。
- 无孤儿 FFmpeg 和不可回收后台任务。
- 非人为网络故障下，无不可解释的录制缺口。
- 所有完成分段可被 ffprobe 读取，抽样解码通过。
- 预览重连不停止录制。
- 自动恢复没有形成高频请求风暴。
- 解析、探测、建连、恢复和导出指标达到发布基线。

精确数值阈值必须在基线阶段写入版本化配置，不应只存在于口头约定。

---

## 7. 基线与对照

抖音现有链路记录：

- resolve_success_rate。
- connect_success_rate。
- time_to_first_media_ms 的 P50、P95。
- reconnect_count 每小时。
- recording_gap_seconds 每小时。
- preview_buffering_ratio。
- segment_validation_failure_rate。
- 正常停止和异常退出后的资源残留。

新链路至少不得在核心录制完整性和资源泄漏指标上劣于对照组。平台特性导致的差异必须记录并评审，不能简单用“平台问题”豁免。

---

## 8. 功能开关

至少提供：

- unified_resolver_v2
- media_probe_v2
- stream_lease_v2
- ingest_supervisor_v2
- segmented_recording_v2
- runtime_events_v2

开关支持按：

- 全局。
- 平台。
- 房间白名单。
- 用户或测试账号。
- 应用版本。

开关配置变更必须可审计。关闭新链路后，不能破坏已创建录制清单的读取。

## 9. 灰度阶段

### 阶段 A：影子验证

- 新解析和探测只记录比较结果。
- 不改变现有主链路。
- 比较候选、画质、首帧成功率和错误分类。

### 阶段 B：内部白名单

- 非抖音平台按迁移顺序接入新链路。
- 开启完整诊断和快速回滚。
- 每个平台独立评估。

### 阶段 C：小比例用户

- 只开放已达到 PREVIEW 的平台。
- 监控错误率、缺口、资源和凭据问题。
- 达到停止条件立即冻结扩大范围。

### 阶段 D：默认启用

- 平台达到 STABLE 后默认使用新链路。
- 保留一个发布周期的旧入口和数据读取兼容。

### 阶段 E：抖音迁移与旧链路退役

- 抖音先影子、后白名单、再默认。
- 旧链路只有在全平台回滚演练完成后才能删除。

---

## 10. 自动停止与回滚条件

出现以下任一情况，停止扩大灰度并评估回滚：

- 录制缺口率显著超过平台基线。
- 分段损坏或导出失败率超过阈值。
- 重连或解析请求出现风暴。
- 预览故障传播到录制。
- 孤儿进程、内存或句柄持续增长。
- 凭据或签名 URL 出现在日志、事件或诊断包。
- 平台接口变化导致大面积结构化解析失败。

回滚方式：

1. 按平台关闭新进样监督器或新解析器。
2. 保留新格式录制资产读取能力。
3. 停止创建新租约，允许安全收尾当前录制。
4. 记录回滚原因、影响版本和恢复条件。
5. 回滚后继续采集只读诊断，不自动反复启用。

---

## 11. 合并与发布门禁

每个实现 PR 必须：

- 关联本系列具体规格。
- 明确影响平台、状态机和兼容入口。
- 增加对应测试。
- 提供日志或事件脱敏证据。
- 说明功能开关和回滚路径。
- 不修改无关用户文件。

发布候选必须：

- 通过 Python 全量测试和前端类型检查。
- 通过故障注入套件。
- 通过至少一个目标平台真实验收。
- 生成版本化指标基线报告。
- 完成一次关闭开关的回滚演练。

---

## 12. 最终完成定义

整个治理项目完成需要同时满足：

1. B站和虎牙达到 STABLE。
2. 快手、斗鱼、小红书、微博至少达到 PREVIEW，并有明确达到 STABLE 的剩余证据。
3. 直链通过安全探测和运行时契约。
4. 抖音完成影子验证且核心指标无明显回退；是否最终切换由评审决定。
5. 录制、预览、恢复、切片、OCR、对齐和导出形成端到端证据。
6. 所有平台专属恢复分支已从公共协调层移除。
7. 新旧数据兼容和回滚路径经过演练。
8. 文档、指标、运行手册和支持等级与实际实现一致。
