## P1-2 ☐ 回看远定位的「字节 0 顺序扫描」结构性问题（两步走）

**现状**（11:36 实测）：定位把 284.7s 目标落到字节 0，顺序啃 236MB 花 15.7s（看门狗保住
不死），但有两个残留风险：
- 高码率 + 1s 分片下，头部 4MB 常只有 1-2 个完整 fragment ⇒ `noteRate` 的 `dt>0.5s`
  条件不满足 ⇒ `bytesPerSec=0` ⇒ `estimateByteOffset` 退化为头部偏移 ⇒ 必然全量顺序扫描；
- 追赶期 `_queue` 无界累积已解析段（实测 ~236MB 段缓冲驻留 JS 堆，内存冲到 78%）——
  长录像 + 更远目标（小时级）可能渲染进程 OOM。

**第 1 步（低风险速效）**：
1. 等待期队列修剪：`_canStartFeeding` 返回 false 期间，丢弃早于目标的已排队段
   （只保留尾部 ~16s），需要时可从文件重读——文件是持久源，段丢弃安全。
2. 头部扫描兜底：`_ensureInit` 后若 `entries.length < 2`，继续追加读一块（至多 16MB）
   直到拿到 ≥2 fragment 或读满上限，保证码率可估。
3. `noteRate` 阈值 `dt > 0.5s` 放宽为 `dt > 0.2s` 且双 entry 时用 `(last-first)` 外推。

**第 2 步（P2，独立评审后再做）**：稀疏检查点索引——把文件按 size 均分 8-16 个探针
窗口（各读 64KB）找 moof/tfdt 建粗索引，定位先落粗索引再微调，消除顺序扫描。
实现收敛在 `LocalFileMseSource`，加开关默认开、失败自动回退现路径。

**防回归 / 红线**：`localFileMseSource.test.ts` 既有 13 条全绿不动；新增：① 队列修剪后
远目标仍出画且时间正确；② 修剪后再次 seek 同位置能正确重读（不黑屏）；③ 队列峰值字节
断言（≤ 上限）。**红线**：三条硬性保证（init 必喂 / 定位失败不死等 / 停滞诊断出口）
不得削弱；回看不得起 ffmpeg / WS 会话（纯渲染端）。

**回滚**：第 1/2 步各自独立成 commit，出问题单独 revert。
