一、项目总览

LSC（Live Stream Clipper）是一个 多直播间录制 + 切片一体化桌面工具：最多 12 路并发录制、4 路 MSE 低延迟预览，支持抖音/B站/虎牙/斗鱼/快手/小红书/微博/直链 8 类源，墙钟精确切片、音频互相关多视角对齐、Valorant OCR 回合 AI 高光分析，可一键导出剪映草稿。定位清晰（CLAUDE.md 明确"不做非线编/特效/推流"），架构分层干净：Electron+React 前端 → Python WebSocket 桥接层 → lsc 核心业务包。

二、检查发现（按严重度）

🔴 P0 — CI 红线当前处于失败状态

CI 的 ruff job 会挂：lint 错误存在于 CI 实际检查的路径中

本地实测 ruff check lsc python-backend tests 报 10 个错误。其中 CI 配置（.github/workflows/ci.yml）只检查 lsc/ python-backend/，这两个目录内有 2 个错误，任何一个都会让 CI lint job 直接红：

  • lsc\core\services\timeline_service.py:71 — B007 循环变量 offset 未使用（唯一不能 --fix 自动修的，需要人工判断是 bug 还是改名）
  • lsc\gui\qt_compat.py:24 — UP035 Callable 应从 collections.abc 导入。注意该文件还是 未跟踪文件，CI 检出后它不存在 → 更微妙：本地过、CI 上不过的组合风险

其余 8 个错误都在 tests/ 目录（未使用 import、import 排序、Yoda 条件），9/10 可 ruff --fix 一键修复。

🔴 P0 — 2 个 Python 测试失败（源码变更后断言未同步）

全量 pytest 实测：1507 个用例，1505 通过，2 失败（99.87%）。两个失败均为「产品代码已正确演进、测试断言没跟上」，不是产品 bug：

失败用例原因修复方式
test_workbench_continuous_analysis_uses_explicit_game_modes源码把 <Radio.Button>无畏契约</Radio.Button> 改成了 {t('无畏契约')}（i18n 化），断言还在匹配旧字面量断言改为匹配 value="valorant_round" + t('无畏契约')
test_sync_analysis_modal_has_no_export_preset_select同上：弹窗 title 由 '持续分析设置' 变为 t('持续分析设置')，测试用旧字符串定位 Modal 失败定位锚点同步更新

这是全量跑出来的（CI matrix 上同样会红）。修两个断言约 5 分钟工作量，但当前就是"仓库不在绿色状态"。

🟠 P1 — 未提交改动规模大，且含关键未跟踪源码

当前工作区 76 个文件已修改未提交（几乎全是前端 + electron 主进程），另有 36 个未跟踪的源码文件，其中关键的有：

  • lsc-electron/src/i18n/ 整个目录（core.ts + 8 个 en.part.*.ts，共 66 KB）— 中英双语系统完全没进 git，一旦误删即丢失全部翻译工作
  • lsc/gui/qt_compat.py — requirements.txt 明确引用的标准库兼容层，未跟踪（CI 上会 ImportError 风险）
  • lsc-electron/scripts/build-msix.ps1 等 3 个发布脚本 — Microsoft Store 发布链路未入库
  • feedback-collector/ 11 个 PowerShell 脚本 — 用户反馈收集工具链未入库

最近一次提交是 08-14，五天的改动摊在工作区里，没有中间 commit，丢工作区=丢全部。

🟠 P1 — 仓库卫生：723 MB 调试文件 + 2.1 GB git 历史

  • 根目录 325 个 _ 开头调试文件共 723 MB（截图 PNG、抽取帧、log dump、3r.mp4 测试视频 217 MB 等），全部被 .gitignore 规则忽略但物理滞留，不清理的话任何全量备份/复制仓库都带着它们
  • .git 目录已膨胀到 2.1 GB（说明历史里提交过二进制大文件），clone 体验很差，建议 git-filter-repo 瘦身 + 大文件走 LFS/网盘
  • nul 文件（Windows 保留名）、test.txt、_shell_ok.txt 等垃圾文件在根目录
  • work/ 目录有 7 个分析脚本 + 2 份 session 报告未跟踪，属于一次性调试产物，应归档或删除

🟡 P2 — 类型安全与静态检查缺口

mypy lsc 实测：22 个文件 87 个错误（配置是 disallow_untyped_defs，说明团队有意收紧但尚未收完），最集中的是 orchestrator.py（None 联合类型未收窄、Any 返回值等）。目前 mypy 在 CI 里会失败吗？—— 会，CI 里 mypy 用默认配置跑，同样报这些错误。

注：我本地跑的是 mypy 2.1.0（项目锁定时代更早的版本可能结果不同），但 CI 装 latest，结论一致：lint job 当前必红。

🟡 P2 — 两个"上帝对象"急需拆分

room_handler.py 已到 8948 行且还在增长（本次未提交 diff 又改了它）。108 个函数塞在一个模块里，其中 _spawn_worker 是 980 行的嵌套闭包（内含整个持续分析主循环状态机），单函数超过很多中小项目的单文件规模。建议按域拆：room_crud / recording / preview / export / analysis / cliplist，每个域一个 handler 文件 + 一个 router。

前端 Workbench/index.tsx 4653 行同理：39 个 state + 26 个 effect 纠缠，虽然已有 memo 比较器惯例兜底，但新功能每加一次都在这个文件里再插一段，出错面持续扩大。i18n 迁移后顺带把 Modal 抽成独立组件会明显改善。

🟡 P2 — i18n 迁移进行中，但硬编码中文仍大量存在

统计显示 Workbench/index.tsx 还有 1157 段中文字符串 未被 t() 包裹，electron/main.ts 有 579 段（菜单、对话框、系统通知）。已完成的 en.part.*.ts 只是翻译资源，键的抽取工作远未完成。现状是"半双语"：界面部分走 t()、部分硬编码，切英文会中英混杂。

五、新功能建议

以下建议均基于现有架构的自然延伸，不违背 CLAUDE.md 的定位边界（不做非线编/特效/推流）。按「价值 × 成本」排序：

#功能价值成本落点
F1AI 切片标题/标签自动生成导出时按 OCR 文本 + 音频能量自动起名（"第X回合 4杀 ACE"），替代人工命名，直接提升发布效率中analysis_handlers + clipNaming.ts 已有一半基础（format_ai_round_clip_label）
F2切片批量发布助手（半自动）生成剪映草稿的同时产出「标题+标签+简介+封面图（抽帧）」套餐，用户一键复制去抖音/B站发布。不做自动发布（违反平台风控），只做内容打包中export_service 已有抽帧能力（frame_capture），补一个模板化文案生成即可
F3AI 高光分析扩展到通用游戏/语音直播现有 pipeline 是 Valorant 专用 OCR；generic_plugin.py 已有雏形。做「弹幕密度峰值检测」类通用信号（弹幕是各平台通用的高光代理指标），把持续分析价值带到非 Valorant 场景高（需求最广）analyzer/generic_plugin.py + 弹幕需要平台 API 接入（B站已有，抖音难）
F4录制磁盘空间水位线告警 + 自动清档12 路 1080p 录制磁盘消耗很快，录制前预估剩余可录时长，低于阈值告警/按策略清最旧档低resource_monitor.py 已监控 CPU/内存/磁盘，补可录时长估算即可
F5切片打点回放（书签系统）录制中按快捷键给"可能精彩"打点，AI 分析后对照打点快速复核，人机协同提效低-中timeline_service + DVR 标记已有类似结构
F6多房间对比同步回放导出前以公共时间轴同时回放 2-4 路（现有多视角对齐已算出 offset，只差同步播放 UI）中前端 previewAudioAligner 已有 offset 数据
F7直播预告/订阅提醒对已添加房间的开播状态做轮询提醒（"XX 已开播，是否一键连接录制"），解决"错过开播"痛点中平台解析层可加开播状态查询
F8导出预设模板（分辨率/平台/命名规则）现 exportPresets.ts 是代码级预设，做成 UI 可编辑模板（抖音竖版、B站横版、双版本同出），减少重复设置低Settings + exportPresets 联动
F9录制健康报告（每房间）导出时附一份「断流次数/重连时长/编码错误」摘要，帮用户识别网络或平台问题低runtime_health.py 已在采集，缺报告化

建议路线

本迭代（1-2 天）：P0 修复 → CI 绿 → 清理仓库 → 提交纪律恢复。
下迭代：F4 磁盘水位线（成本最低、痛点直接）+ F8 导出预设模板 + F9 健康报告（三者都复用现有采集数据）。
再之后：F1 AI 命名（配合现有 AI 分析链路）+ F3 通用高光信号，同时启动 room_handler 拆分。
